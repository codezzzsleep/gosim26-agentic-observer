# 给本地 AI 的任务说明：survey26 本地闭环实验环境

> **10 月 6 日晚更新：** 工作核心 `agent/` 已换成 v3（v2 核心 + 提速 + 真实时间守卫），v2 核心在 `baselines/v2/`。先读 `UPDATE-1006b.md`。

你在一个完整的本地实验环境里工作，目标是把一个已经在线上排名靠前的参赛智能体继续做强，并保证它在**没见过的隐藏卡**上稳定。
这台机器是 16 核 32 GB。重的测试都由你在这里跑；这个环境的作者只有 2 核，很多东西只做了冒烟验证，第 11 节列出了哪些没验证过。

## 2. 比赛规则要点

- 协议 `participant-agent-protocol-v4`：标准输入/输出每行一个 JSON。每次决策回 `observe` / `wait` / `report` / `finish` 之一。
  **非法动作或程序崩溃，整张卡以 agent_error 结束。**
- 线上榜：10 月 6 日起每次评测同时跑 A–D 和新增的 A1–D1 共 8 张卡。原总榜仍按 A–D；新设超级总榜按 8 张卡之和。
  A1–D1 规则和接口不变，"观测条件更贴近真实观测站"，具体差别未公布。**最终排名不变：隐藏卡 E–H，每张评 3 次取平均。**
  隐藏卡和 A–D 相同的是协议、计分规则、时间限制、事件种类；不同的是天气和事件时间、季节和月相、目标和天区、难度侧重，
  "变化幅度和 A–D 差不多"。所以策略不能照着 A–D 写死。
- 时间：每张卡 900 秒，只算智能体回合内的 CPU 时间并按机器速度折算；等模型、等网络不计。另有 30 分钟实际时间上限。
- 运行环境：独立 Linux 容器，2 核、2 GB 内存、最多 128 个进程；根目录只读，可写 `/workspace` 和 `/tmp`（256 MB）；构建最长 10 分钟。
- 额度：每队每天 50 次评测、50 次版本准备，最多同时 4 个。练习赛不关闭，次数另算，可以单卡调试。
  平台有「评测 3 次取平均」选项，用来检查稳定性。
- **截止前必须手动选好「最终版本」。** 自动最佳现在是 v1（无模型）。最终版本必须是带模型环节、且平台日志里确实调到模型的版本。
- 获奖资格：至少两个环节由大模型驱动（自然语言理解、数据解析、任务规划、行动决策、工具调用、计划自适应中的任意两项），
  评审主要读最终代码。获奖需开源（MIT/Apache）。
- 所有决策必须由程序自动做出。项目 ZIP ≤ 50 MB。
- 模型：在平台「密钥与网络」里添加模型服务，密钥以环境变量交给程序。`llm_stages/llm.py` 按
  `DEEPSEEK → OPENAI → KIMI → MOONSHOT → 其他带 _BASE_URL 的前缀 → ANTHROPIC` 的顺序自动选一组
  `NAME_API_KEY / NAME_BASE_URL / NAME_MODEL`；`AO_LLM_PREFIX=NAME` 可强制指定。

### "天气不公开"的意思

官方卡的 ZIP 里**只有公开输入**（目标表、天区轮廓、观测日程、光纤和计分配置），没有天气、事件和限时请求。
练习卡 α–δ 的 ZIP 也是这样。不是没有天气：运行时照样每 15 分钟一条简报，天气照样影响得分。
后果是官方卡本身不能在本地打分。这个环境的做法是**用官方卡的真实目录，配上官方公开的天气模拟器生成的天气**，见第 4 节。

## 4. 任务卡：84 张，分四层用

所有卡的天气、事件、限时请求都是用官方公开的模拟器按种子生成的，规则和平台一致，但**不是任何官方卡的真实天气**。
每张卡由 `cards/SETS.json` 里的一条配方完全决定，谁造出来都一样。

| 卡集 | 张数 | 是什么 | 规模 |
|---|---:|---|---|
| `smoke` | 4 | A、B、C、D 的真实目录，只取前 8 夜 | 几分钟跑完，只用来查崩溃和超时，分数无意义 |
| `dev` / `hold` | 8 / 8 | 自造目录，练习卡规模 | 32–38 夜，约 1 万目标，4×4 光纤 |
| `prac_dev` / `prac_hold` | 4 / 4 | 练习卡 α β γ δ 的真实目录 + 模拟天气 | 38 夜，约 1 万目标，4×4 |
| `real_dev` / `real_hold` / `real_test` | 8 / 8 / 8 | 正式卡 A B C D 的真实目录 + 模拟天气，每张卡 2 个天气种子 | 121–365 夜，3–5 万目标，3×3 到 10×10 |
| `var_dev` / `var_hold` / `var_test` | 12 / 12 / 8 | **隐藏卡式的变化**：站点、季节、赛季长度、目标数、光纤格数和大小、计分零点、亮度分布、压力场景都随机 | 100–365 夜，2–5 万目标，3×3 到 10×10 |

分组（`bench.py`、`exp.py` 的 `--set` 可以直接写组名）：

| 组 | 包含 | 用途 |
|---|---|---|
| `quick` | dev + prac_dev（12 张小卡） | 最快的反馈，每个想法先在这里试 |
| `tune` | real_dev + var_dev（20 张大卡） | 主战场：A–D 规模上调参看这里 |
| `confirm` | hold + prac_hold + real_hold + var_hold（32 张） | 只在准备采纳一个改动时跑一次；这里变差就不采纳 |
| `test` | real_test + var_test（16 张） | 封存。只在定最终版本前跑一次，之后不再根据它改任何东西 |

为什么要 `var_*`：`real_*` 用的是 A–D 的真实目录，在上面调参等于对 A–D 的目标和天区做了适配，而隐藏卡会换目标、天区、季节和站点。
`var_*` 每张卡都是不同的站点（含北半球和赤道）、不同的光纤布局和不同的规模，更接近"再抽四张"的情形。
两类卡都要看；只在一类上变好、另一类上变差的改动要警惕。

真实 A–D 的参数（来自官方卡文件）：

| 卡 | 站点纬度 | 夜数 | 目标数（必观测） | 光纤 | 每格面积 | f0 × T0 | 其他 |
|---|---:|---:|---:|---|---:|---|---|
| A | −24.6° | 123 | 30,000（1,500） | 4×4 | 0.4 deg² | 0.5 × 900 | |
| B | −33.9° | 183 | 50,000（2,500） | 5×5 | 0.064 deg² | 0.8 × 1000 | 类星体很亮（中位数 2.97） |
| C | +19.8° | 121 | 30,000（1,500） | 3×3 | 0.7 deg² | 0.5 × 900 | 北半球 |
| D | −45.0° | 365 | 30,000（1,500） | 10×10 | 0.06 deg² | 0.5 × 900 | 可能有一次数据丢失（`state_resync`） |

加卡：往 `cards/SETS.json` 里加配方（换新种子），然后

```bash
python3 tools/make_cards.py            # 造出缺的卡
python3 tools/make_cards.py --record   # 把新卡记入校验文件
python3 tools/make_cards.py --list     # 看所有卡的夜数、目标数、光纤、纬度、压力场景
```

样本越多，对隐藏卡的估计越稳。如果某个结论在现有卡上是 UNCLEAR，就加卡再跑，不要靠猜。
大卡跑一张要十几分钟甚至更久（D 规模最久），加卡时注意总耗时。

## 5. 闭环：每个改动都走这一圈

```
改代码或换参数 ─→ exp.py 在 quick 上跑 ─→ 看结论 ─┬─ WORSE / 无益 ─→ 丢弃，记一笔
                                                  └─ BETTER / 有希望 ─→ exp.py 在 tune 上跑 ─→ BETTER ─→ exp.py 在 confirm 上跑
                                                                                                          └─ 不变差 ─→ 采纳，改默认值
准备上传 ─→ gate.py（组装、单元测试、冒烟、等价性、假模型）─→ 通过 ─→ 上传评测 ─→ 把平台分数记进 results/PLATFORM.md
```

### 5.1 一次实验 = 一条命令

```bash
python3 tools/exp.py --tag kappa085 --base v1 --set quick --agent-dir agent --env AO_FIXED_EFFORT=1 AO_KAPPA=0.85 --note "提高时间价格"
```

它依次做：基线缺哪些卡就先补跑 → 跑新版本（已有结果的卡不重跑）→ 健康检查 → 和基线逐卡配对比较并给出结论 → 往 `results/LEDGER.md` 追加一行。

结论的含义（`tools/compare.py`）：对每张卡算新版本相对基线的百分比差，对卡做重采样得到平均差的 95% 区间。

| 结论 | 含义 | 怎么办 |
|---|---|---|
| BETTER | 整个区间在 0 以上 | 进入下一层卡集 |
| WORSE | 整个区间在 0 以下 | 丢弃 |
| NO DIFFERENCE | 区间落在 ±0.3% 以内 | 没有效果，丢弃（除非它让代码更简单或更稳） |
| UNCLEAR | 其他情况 | 卡不够，或者改动在不同卡上效果相反。加卡，或者看逐卡明细找原因 |

一个标签对应一个智能体目录加一组环境变量。换参数就换标签。`exp.py` 发现同一标签下的智能体代码或环境变了会拒绝运行。
基线要放在不变的目录里（`baselines/`、`build/`），否则补跑基线时会被拒绝。

### 5.2 两种运行方式，别混用

- **固定搜索力度** `AO_FIXED_EFFORT=1`：同一份代码的决策可以逐字节复现，差别只来自改动本身。
  **只适合小卡（quick、hold、prac_hold）**。
- **节奏控制开着**（不设 `AO_FIXED_EFFORT`）：智能体按剩余 CPU 预算自己调搜索力度，这是平台上的真实行为。
  **大卡（tune、confirm 里的 real 和 var、test）必须这样跑**，因为力度固定在 1 时大卡会超出 900 秒预算，整张卡提前结束。
  这种方式下同一份代码两次运行的分数会有小差别。先做一次 A/A 测试量出这个噪声（第 9 节 P0）。

### 5.3 健康检查

```bash
python3 tools/health.py 标签 [--set tune]
```

FAIL：没有分数、没有正常结束、日志里有内部错误、CPU 计费超过 800 秒、实际耗时超过 1500 秒。
WARN：CPU 计费超过 680 秒、实际耗时超过 900 秒（平台容器只有 2 核，比这台机器慢）、有扣分的误报、必观测目标漏得多。
任何 FAIL 都要先修，再谈分数。隐藏卡上一张卡记 0 分，比任何调参的收益都大。

### 5.4 上传前把关

```bash
python3 tools/gate.py --core baselines/v1 --llm --name v1_llm     # v1 核心 + 模型环节
python3 tools/gate.py --core agent --llm --name next_llm          # 新核心 + 模型环节
```

把关依次检查：组装并打包（用平台自己的打包代码读回来，查大小、清单、有没有密钥）→ 单元测试（几何与官方引擎一致、天空跟踪器、
故障裁决路径）→ 四张冒烟卡正常结束 → 关掉模型时分数和核心逐卡完全相同 → 假模型的 good / garbage / error / slow 四种模式下运行都健康，
且 good 模式下模型的答案确实被采纳。全部通过才会打印 `GATE PASSED` 和 ZIP 路径。

上传和评测由用户决定，**不要写循环自动提交**。每次评测后：
1. 打开任意一张卡的日志，找 `model stages on:` 和 `llm night briefing`。没有这些行，说明平台没把密钥交给程序，这次其实是纯规则。
2. 把版本名、四张卡的分数、CPU 用时记到 `results/PLATFORM.md`。
3. 对照本地 `real_dev` 上同一版本的排名：本地说更好的版本，平台上是不是也更好？这是在校验本地环境本身。

## 7. 智能体的设计（照这个思路继续，不要推倒重来）

核心是数值规划加贝叶斯状态估计，大模型只在少数需要"读懂情况"的节点介入，而且作用范围有上下界。

**规则核心（`agent/`）**
- `agent.py` 协议主循环。`ingest()` 处理公报、观测结果、上报结果、`state_resync`；`_respond()` 决定动作；`_pace()` 按剩余 CPU 预算分级调整搜索力度；
  `_maybe_report()` 故障上报策略；圆顶关闭的探测逻辑。三层保护：动作发出前经过 `validate()`；决策抛异常时退回一个合法的 `wait`
  并计数（日志末尾的 `internal_errors=`）；模型出问题退回规则。**这三层不要拆。**
- `planner.py` 一次搜索同时定指向、光纤分配、曝光时长、观测程序。对所有可见目标 × 约 20 种时长算收益，在几十个锚点周围试几百个指向偏移，
  用和引擎完全相同的切平面几何把目标映射到光纤格子，每格取收益最大的目标，选 `总收益 − 时间价格 × T` 最大的方案，再细网格微调。numpy 向量化。
  **赛季计划（`_season_plan`）**：每个目标只计最好的一次曝光，所以"以后还要重做"的半截曝光基本是浪费。程序估计剩余赛季能完成哪些目标、
  一个光纤秒值多少分，据此给"现在做完"和"顺带拍一点"定价（在小卡上带来 +3–4.5%）。必观测目标的奖励随赛季推进逐步加大。
- `tracker.py` 在（天气水平 W、仪器效率 eta、是否有故障）的网格上做贝叶斯滤波。天气同时影响完成因子和程序档位，仪器效率只影响完成因子，
  据此把两者分开；并区分地震（有公报、逐夜恢复、不可修）、仪器故障（无公报、持续到上报为止）、圆顶临时关闭（无公报、短暂）。
- `hazards.py` 公报里的方向性事件：地形遮挡（永久）、火箭发射、局部天气。
- `pointing.py` 隐藏的指向偏差：用"指派的目标命中/未命中"做似然估计。
- `state.py` 目标目录、已得分数、可重放的曝光账本（数据丢失后重建状态）。`skymath.py` 天球几何（与引擎对比误差 1e-13）。

**模型环节（`llm_stages/`）**
- `llm.py` 聊天客户端：OpenAI 兼容和 Anthropic 两种协议，纯标准库，后台线程，重试；密钥从不写日志。
- `advisor.py` 三个环节的提示词、工具定义、答案校验。`supervisor.py` 把校验过的答案应用到规划器。
- 三个环节：每晚开始的**夜间简报**（读预报和公报，定今晚避开的方位、保守度、必观测目标加紧或暂缓）；
  有代价时的**故障裁决**（读最近曝光的证据，可否决一次有代价的上报）；每 4 晚一次带**工具调用**的赛季复盘（调整规划器"把目标留到能一次拍完"的强度）。
- 等待模型不占 CPU 预算。每晚开始最多等 10 秒，并且按剩余实际时间自动缩短（`_spare_wait`）。整张卡最多 600 次请求；
  长赛季自动拉开简报和复盘的间隔。工具调用先用原生方式，服务不支持时自动改用纯文本形式。
- 平台在"本次不提供模型"的评测里设 `OBSERVER_MODEL_DISABLED=1`，此时自动纯规则。
- 日志里每 10 晚和结束时各有一行 `model stages: ... calls= ok= failed= waited= applied: ...`，用它确认模型环节真的在工作。

**目录约定**：核心只有一份（`agent/`），模型环节只有一份（`llm_stages/`），提交包由 `tools/assemble.py` 组装到 `build/`。
不要在 `build/` 里改文件，也不要把核心文件复制出第二份去改。

**`agent/` 相对 v1 多的四项改动**（每项都有开关可回退）：

| 改动 | 开关（回到 v1 行为） | 说明 |
|---|---|---|
| 指向偏差估计器 | `AO_OFFSET_UNKNOWN_MARGIN=0` 只能部分回退 | v1 用较粗的办法估偏差 |
| 地形遮挡范围学习 | 无开关 | 用零分命中学被挡的方位和高度范围 |
| 圆顶探测可用任意目标 | `AO_PROBE_ANY=0` | v1 里可见目标都已有成绩时不出手探测，会整晚停在"疑似关闭" |

这四项只在一张小卡（h203）上看过：6335 → 6414，空等消失。**是否整体更好，要你来回答（第 9 节 P1）。**

已经从公开的生成器代码确认的事实（写策略时可以依赖）：仪器故障把效率乘以 0.4–0.7（压力场景 0.3–0.5），不公告，**持续到上报为止**；

### P3 A–D 规模上的提升线索（按预期收益排序）

1. **光纤边缘余量是按度写死的，小光纤上代价很大。** `EDGE_MARGIN=0.02°` 是在 0.63° 宽的格子上定的。B 的格子宽 0.253°，D 是 0.245°，
   两边各留 0.02° 之后可用面积只剩约 71%；`var` 卡里还有 0.15° 宽的格子。而 B、D 上每格平均只有 0.3–0.4 个目标，
   能不能把目标放进格子正是这两张卡的关键（冒烟卡上 B 每次曝光只填上 25 根里的 6–8 根，D 填上 100 根里的 40–46 根）。
   作者在冒烟卡 B8 上量过一次（新核心，固定力度）：`AO_EDGE_MARGIN` 从 0.02 改到 0.003，8 夜的目标得分 5204 → 5719（+9.9%），
   漏掉的必观测目标 1610 → 1563；D8 上目标得分 1560 → 1794（+15%）。只是两张 8 夜的短卡，方向明确但幅度要你在 `tune` 上量。
   先试 `AO_EDGE_MARGIN=0.003`，再考虑把余量改成格子宽度的比例；有压力场景的卡在估出指向偏差之前仍需要较大的余量
   （新核心在偏差未知时另加 `OFFSET_UNKNOWN_MARGIN × OFFSET_RADIUS_SHARE = 0.014°`，同样值得按格子宽度重新定）。
2. **CPU 效率就是分数，D 型卡尤其如此。** 冒烟卡上力度为 1 时每次决策的 CPU：C8 约 0.13 秒，B8 约 0.2 秒，A8 约 0.3 秒，**D8 约 2.3 秒**
   （158 次曝光计费 366 秒）。D 有 365 夜，要在 900 秒内跑完，力度必须被 `_pace()` 降很多档，搜索质量随之下降。
   原因在 `planner.py` 的粗搜索：每个锚点周围的指向偏移网格是按"整个视场 ÷（格子宽度 ÷ `COARSE_STEP`）"取点的，
   点数和光纤数成正比（A 是 21×21，D 是 57×57）。但目标落在哪个格子里对偏移是以格子宽度为周期的，
   没必要用格内分辨率扫遍整个视场：可以只在一个格子宽度内细扫对齐，再配少数几个视场级的偏移。
   便宜的第一步是直接试 `AO_COARSE_STEP=3`（偏移点数降到四分之一）。
   用 `tools/inproc.py --profile` 确认热点；对比 `AO_FIXED_EFFORT=0.35 / 0.22 / 0.12` 在大卡上的分数，量出"力度换分数"的斜率
   （官方说 Rust 版示例的 CPU 用量是 Python 版的 1/30，说明主办方也认为 CPU 是紧的）。`MAX_VISIBLE`（默认 9000）在 5 万目标的卡上也要试。
   每次运行日志最后一行的 `effort=` 是结束时的力度档位。
3. `CPU_SHARE`（默认 0.70）：A 规模上实际计费到过 695 秒。量一下各卡的计费分布，决定要不要留更多余量。
4. 赛季计划和必观测目标的参数（`PLAN_*`、`REQ_*`、`KAPPA`）是在 35 夜的小卡上定的，长赛季上重新扫一遍。
   大卡上必观测目标有 1,500–2,500 个，每漏一个 −50，量级很大。
5. 小卡上遗留的想法：`AO_SEASON_PLAN=2`、`AO_PLAN_PI=0.6`、`AO_PLAN_UTIL_ADAPT=1`、`AO_PRICE_MODE=plan`、`AO_KAPPA=0.85/0.45`、
   `AO_REQUIRED_SIGMA=0.10 AO_REQUIRED_AIM=1.03`、`AO_FIRST_LOOK_SECONDS=600`；诊断模式的短曝光应当选在没有方向性事件的干净天区。

新参数尽量写成无量纲的形式（相对格子宽度、相对赛季长度、相对 f0·T0），因为隐藏卡的规模和 A–D 一样多变。

## 10. 实验纪律

1. 只看多张卡的平均和区间，不看单卡。单张小卡的运行差别约 ±1%。
2. `quick` 和 `tune` 用来调；`confirm` 只用来确认；`test` 封存到最后。调参时偷看 `confirm` 或 `test`，它们就不再是没见过的卡了。
3. 一次只改一件事，每个改动配一个环境变量开关，默认值只在 confirm 通过之后才改。
4. 不要针对某张卡的天气、目标、站点、日期写特殊逻辑。智能体只根据运行时收到的信息做决定。
5. `real_*` 和 `var_*` 都要看。只在 `real_*` 上变好的改动可能只是适配了 A–D 的目录。
6. 稳定性优先于分数：任何 health FAIL 先修。改完核心跑一次 `smoke`。
7. 密钥只放在 `.env` 或环境变量里，不进 ZIP、不进日志、不进仓库。平台令牌只从环境变量 `SURVEY26_TOKEN` 读。
8. 不要写循环自动上传或自动评测。每次上传和评测前先问用户。
9. 每个结论都要有 `LEDGER.md` 里的一行作依据。没跑的、没验证的要明说。
