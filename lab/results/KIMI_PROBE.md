# Kimi 中转实测（10 月 6 日，用户本机运行 `probe_kimi.py`）

服务：组委会的 Kimi 中转，模型 `kimi-for-coding`。用的是智能体里的真实提示词。

| 测试 | 结果 |
|---|---|
| 基本调用 | 通，3.9 秒。回复里有 `content` 和 `reasoning_content`；`usage` 里有 `reasoning_tokens`。没有限流或额度相关的响应头 |
| 夜间简报 | 通过，25 秒。答案在正文里，是合法 JSON，读对了 SE 方向的霾。推理用掉约 960 个 token |
| 故障裁决 | 通过，18 秒。判为 fault，把握 0.88，理由正确 |
| 原生工具调用 | 通过，两轮共 15 秒。第一轮一次并行调用了全部 4 个工具；不需要把推理内容带回 |
| 文本形式的工具调用 | 通过，五轮共 26 秒（每轮一个工具） |
| 回答上限 | 300 token 不够（推理用完了，答案被截断）；1500 够 |
| 带 temperature | 中转直接返回 HTTP 400。程序不传 temperature |
| 同时 6 个请求 | 只有 2 个成功，4 个 HTTP 429 |
| 同时 12 个请求 | 只有 2 个成功，10 个 HTTP 429。成功的那些最长等了 48 秒 |

由此得到的设计结论（已落实在 `llm_stages/`）：

1. 三个环节的提示词和解析方式都和 Kimi 对得上，原生工具调用可用。
2. 一次回答 15–30 秒，相当于模拟里的好几个夜晚，所以咨询必须停下来等，而且只能是少量的。
3. 中转大约只允许 2 个并发。正式评测是 8 张卡同时跑、共用一个密钥，所以每张卡同一时刻只发一个请求，遇到 429 耐心重试；
   即便如此，各张卡能拿到的回答数也会比单独运行时少。
