# Agentic Observer — 巡天观测智能体

GOSIM 2026 Agentic Observer Hackathon（https://create.gosim.org/survey26/）的完整参赛项目，
协议 `participant-agent-protocol-v4`（标准输入/输出上每行一个 JSON 对象）。

数值规划器负责每一次曝光决策；大模型在三个需要"读懂情况、做判断"的环节工作（见下文"大模型环节"）。
没有配置密钥，或评测时选了「本次不提供模型」（`OBSERVER_MODEL_DISABLED=1`）时，程序自动退回纯规则运行。

## 目录

```
agent.py               入口：协议主循环、结果处理、故障上报、CPU 节奏控制、真实时间守卫
planner.py             规划器：一次搜索同时决定指向、光纤分配、曝光时长和观测程序
tracker.py             天空/仪器状态跟踪：在（天气水平 W、仪器效率 eta、是否有故障）上做贝叶斯滤波
hazards.py             公报里的方向性事件：地形遮挡、火箭发射、局部天气
pointing.py            指向偏差估计（Hard mode）：用命中/未命中结果在偏差网格上做似然估计
state.py               目标目录、已取得的成绩、可重放的曝光账本（用于数据丢失后的状态恢复）
skymath.py             公开的天球几何公式（恒星时、地平坐标、月亮、大气质量、光纤切平面）
supervisor.py          大模型环节与智能体状态之间的接线：收集材料、发起调用、把校验过的答案应用到规划器
advisor.py             三个大模型环节的提示词、工具定义和答案校验
llm.py                 聊天客户端（OpenAI 兼容协议和 Anthropic 协议，纯标准库，后台线程）
observer.project.json  平台清单（构建时安装 numpy，运行 python3 -u agent.py）
requirements.txt       唯一的第三方依赖：numpy
pack_agent.py          打包成可上传的 ZIP
```

## 它怎么做决策

1. **规划（planner.py）。** 每次决策对所有当前可见的目标、20 种候选曝光时长计算收益，然后在
   三十个左右的锚点周围各试几百个指向偏移，按评测引擎完全相同的几何把目标映射到光纤格子，
   每根光纤取格内收益最大的目标；选 `总收益 − 时间价格 × T` 最大的方案，再在细网格上微调。
   一次决策评估上万个（指向，时长）组合。
2. **赛季计划。** 同一目标只计最好的一次曝光，所以"以后还要重做"的半截曝光基本是浪费。程序估计
   剩余赛季能完成哪些目标、一个光纤秒值多少分，据此区分"现在做完能省下以后时间"的目标和
   "只能顺带拍一点"的目标。必观测目标的奖励按"以后来不及做的风险"计入，随赛季推进逐步加大。
3. **天空与仪器跟踪（tracker.py）。** 天气同时影响完成因子和观测程序档位，仪器效率只影响完成因子。
   程序据此从自己的曝光结果里分离两者，并区分三种效率变化：地震（有公报、逐夜恢复）、
   仪器故障（无公报、持续到上报为止）、圆顶临时关闭（短暂、之后恢复）。
4. **故障上报。** 当"存在未修复故障"的概率持续偏高，且期望收益（修复后的增益 × 概率）大于
   误报代价时才上报；免罚次数用完后门槛更高，并限制付费误报的次数。
5. **指向偏差（Hard mode）。** 用每个已指派目标的命中/未命中结果，在偏差网格上做似然估计，
   通常两次曝光后就能修正。
6. **数据丢失（Hard mode）。** 收到 `state_resync` 后按失效窗口重放自己的曝光账本，恢复每个目标的
   最高分和完成因子。
7. **CPU 节奏。** 用 `time.process_time` 计量每次决策的 CPU 时间，与
   `wallclock.remaining_real_cpu_seconds` 比较；只有明显超出预算时才分级降低搜索力度。

8. **真实时间守卫。** 评测引擎每一步都要遍历已经记分的全部光纤记录，所以赛季越往后引擎自己越慢；这部分时间不计入
   CPU 预算，但计入真实时间硬上限（`wallclock.wall_remaining_seconds`），到上限整场结束。程序测量每次应答之后到下一次请求
   之间的真实时间，对"已指派的光纤总数"做最小二乘拟合，每 50 次决策预测一次剩余赛季需要的真实时间。预测超出剩余时间的
   85% 时沿一个固定的阶梯让步：先降低搜索力度上限，再规定普通曝光的最短时长（曝光更少更长，引擎步数和记录数都减少）；
   连最高一级也装不下时，按预计能跑到的时刻而不是日历上的赛季末来安排必观测目标。时间够用时守卫不做任何事。

程序只使用协议下发的公开信息（目录、公开评分配置、公报、预报、自己的观测结果），不读取任何卡片文件。

## 大模型环节

| 环节 | 对应能力 | 模型读什么 | 模型决定什么 | 生效范围 |
|---|---|---|---|---|
| 夜间简报 | 自然语言理解、计划自适应 | 今晚和之后几晚的预报、当前公报、近几晚天空水平、必观测目标余量 | 今晚避开哪些方位、曝光是否保守、必观测目标是加紧还是暂缓 | 只能避开公告点名的方位；保守度和加紧/暂缓各有固定档位 |
| 故障裁决 | 数据解析、行动决策 | 最近 24 次曝光的时间、时长、估计的天气水平 W 和仪器效率 eta、公报、误报代价 | fault / not_fault / unsure | 上报有代价时才问；可以否决一次上报（之后 3 小时内不再上报）；不能突破付费误报次数上限 |
| 赛季复盘 | 任务规划、工具调用 | 自己调用工具查询：进度、近期天空、必观测目标状态、预报 | hold_strength：规划器多大程度上"把目标留到能一次拍完" | 在规则默认值上下各 0.10 的范围内调整 |

代码位置：提示词、工具定义和答案校验在 `advisor.py`；把答案应用到规划器在 `supervisor.py`；聊天客户端在 `llm.py`。

- **咨询是"暂停—等待—继续"**：推理模型一次回答要 15–30 秒，而模拟里的一整晚只需几秒真实时间，所以不能边跑边等。
  每次咨询时巡天暂停，等到答案再继续。等待不占 CPU 预算，占的是真实时间，因此按真实时间管理：
  - 程序实测每次决策的真实耗时，并采用真实时间守卫对剩余赛季的预测，绝不动用剩余巡天在实际时间上限之前还需要的时间（另留 150 秒余量）；
  - 每张卡等待模型的总时间不超过 300 秒（`AO_MODEL_WALL_BUDGET`）；
  - 咨询因此是少量的、放在关键位置的：赛季的 12%、35%、60%、82% 处各复盘一次；把赛季分成 6 段，每段里第一个有新公告的夜晚做一次简报；
    上报有代价时做一次裁决。
- **同一时刻只发一个请求，被限流就耐心重试**：多张卡同时评测时共用一个密钥，遇到 429 会带随机间隔地退避重试，直到这次咨询的等待上限。
  各张卡的咨询时点带一点随机偏移，避免同时发问。
- **工具调用的两种方式**：先用服务的原生工具调用（`tools` 字段）；如果服务拒绝带工具的请求，或者模型把工具请求写在正文里，
  自动改用同一协议的纯文本形式（模型回 `{"tool": ..., "arguments": ...}`，程序执行后把结果作为下一条消息发回）。
- **容错**：超时、限流、返回内容不是合法 JSON、数值越界时，一律保留规则默认值，程序不会因此出错或停顿。
  答案在正文为空时会到 `reasoning_content` 里找。回答上限 3000 token（推理要用掉一部分）。请求里不带 temperature（有的服务会拒绝）。

### 配置模型

在平台「密钥与网络」里添加模型服务（或本地写进 `.env`，见 `.env.example`）。程序按一组同前缀的环境变量识别服务：
`NAME_API_KEY`、`NAME_BASE_URL`、`NAME_MODEL`。

- 自动选择的顺序：`KIMI` → `OPENAI` → `DEEPSEEK` → `MOONSHOT` → 其他同时带 `_API_KEY` 和 `_BASE_URL` 的前缀 → `ANTHROPIC`（Anthropic 协议）。
- 配置了多家服务时先用第一家；如果连续两次咨询都没有得到回答，自动换到下一家（循环），所以某一家服务中断不会让模型环节整体失效。
- `AO_LLM_PREFIX=NAME` 强制使用某一组。
- DeepSeek 只需要 `DEEPSEEK_API_KEY`，地址和模型默认是 `https://api.deepseek.com` 和 `deepseek-chat`。
- `OPENAI_*` 可以指向任意 OpenAI 兼容服务；`KIMI_API_KEY` 没有自己的地址时沿用 `OPENAI_BASE_URL` / `OPENAI_MODEL`。

运行日志开头有一行 `model stages on: provider ... model ...`，之后每 10 晚和结束时各有一行
`model stages: ... calls= ok= failed= waited= skipped= latency~ applied: ...`，据此确认模型环节确实在工作。密钥不会写进日志。

## 本地运行

需要 Python 3.9+ 和 numpy：

```bash
pip install --target .deps -r requirements.txt        # 或者直接 pip install numpy
python3 <官方示例包>/runner/run_local.py --inherit-env --card <官方示例包>/local-cards/L1 \
        --agent "python3 -u agent.py" --agent-cwd .
```

## 打包上传

```bash
python3 pack_agent.py --out ../observer-agent.zip
```

在「参赛」页上传 ZIP，或用命令行：

```bash
survey26 project upload observer-agent.zip --title "observer agent"
survey26 project wait <版本>        # 构建 + 公开场景测试，不占评测次数
survey26 project confirm <版本> --yes
survey26 eval start <版本> --yes
```

想对比有无大模型的差别，评测时勾选「本次不提供模型」/ 加 `--no-model` 即可得到纯规则的成绩。

## 可调参数

`planner.py` 和 `agent.py` 顶部的常数都可以用 `AO_<名字>` 环境变量覆盖，例如
`AO_KAPPA=0.7`、`AO_FIXED_EFFORT=1`（固定搜索力度，便于复现对比）。
